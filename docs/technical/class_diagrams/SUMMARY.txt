KEY DESIGN PATTERNS
================================================================================

DOMAIN
  • Entities with dataclass + invariant validation
  • Frozen value objects (Money, Quantity, etc.)
  • Abstract repository ports
  • Domain services (RecipeDependencyValidator, PreferenceMatcher)
  • Cycle detection (DFS with backtracking)
  • Nesting depth limits (max 5 levels)

APPLICATION
  • CRUD base classes eliminate 500+ lines boilerplate
  • One class = one operation (single responsibility)
  • Ownership verification on every query
  • DTOs bridge API and domain
  • Pagination (PAGE_SIZE=25, offset-based)
  • Business rule validation

INFRASTRUCTURE
  • BaseOrmRepository[E, I] generic template
  • Separate create/update/retrieve methods
  • Registry pattern for extensible exporters/importers
  • Multi-database support (SQLite/PostgreSQL)
  • JSON columns for flexible data
  • Cascade deletes for referential integrity

API
  • Dependency injection via FastAPI Depends()
  • Bearer token authentication (JWT)
  • Exception handlers (domain errors → HTTP status)
  • Pydantic validation
  • Converter functions decouple layers
  • Stateless (container per request)

================================================================================
DATA MODEL HIGHLIGHTS
================================================================================

USER MANAGEMENT
  • User → 1:N RefreshToken (JWT rotation)
  • User → 1:N FamilyMember (family members with portion multipliers)
  • User → 1:N Preference (dietary/lifestyle preferences)
  • FamilyMember → N:M Preference (assignment via preference_ids JSON)

RECIPES
  • Recipe → 1:N RecipeIngredient (products or sub-recipes)
  • Recipe → 1:N CookingStep
  • Recipe ↔ Recipe (nested recipes: sub_recipe_id in ingredient)
  • Recipe → RecipeCategory
  • Validation: circular dependency check, depth limit (max 5)

PRODUCTS
  • Product → ProductCategory
  • Product used in RecipeIngredient
  • Product in MenuSlot (direct product-only slots)

MENUS & PLANNING
  • Menu → 1:N MenuSlot (grid: day 0-6 × meal_type × position)
  • MenuSlot → Recipe OR Product (exactly one)
  • MenuSlot → MealType
  • MenuSlot.member_ids (JSON list: which family members this meal is for)
  • Supports individual menu mode (member-specific meals)

SHOPPING LISTS
  • Menu → ShoppingList (generated, ephemeral)
  • Menu → SavedShoppingList (persistent, with source menu link)
  • SavedShoppingListItem → Product (or product_name if deleted)
  • Aggregation: recursive product resolution from recipes

MEAL TYPES
  • MealType.is_system: 3 default (Breakfast 8:00, Lunch 13:00, Dinner 18:00)
  • MealType.is_system=False: user-custom, max 10 per user
  • MealType.time: HH:MM for display ordering
  • MealType.sort_order: secondary sorting

================================================================================
AUTHENTICATION & AUTHORIZATION
================================================================================

REGISTRATION
  • User created with bcrypt-hashed password
  • Default FamilyMember created (user as family member)
  • 3 system MealTypes auto-created

LOGIN
  • Email + password validated
  • Access token issued (30 min expiry, HS256)
  • Refresh token issued (raw 64-byte random, hashed to DB, 30 day expiry)
  • Login timestamp updated

TOKEN REFRESH
  • Refresh token validated (not expired, not revoked)
  • Old refresh token revoked
  • New token pair issued (rotation)

AUTHENTICATION
  • Bearer token extracted from Authorization header
  • Token validated (signature, expiry)
  • User ID extracted
  • User loaded for request context

AUTHORIZATION
  • Every query filtered by user_id
  • Ownership checks on get/update/delete
  • FamilyMembers, Preferences isolated per user
  • Recipes, Products isolated per user

EXPORT & IMPORT
================================================================================

EXPORT
  • Registry-based plugin architecture
  • Formats: CSV, JSON, PDF
  • Entities: Recipes, Products, ShoppingLists, Menus
  • Bytes returned (for HTTP download)

IMPORT
  • Registry-based plugin architecture
  • Formats: CSV, JSON
  • Entities: Recipes, Products, Menus
  • Upsert semantics (create or update by name)
  • ImportResult: counts of created/updated + error list
